## Root cause — auth-worker side (blocks step 3-5)

`POST /mcp/pair/new` は 200 を返す (rate-limit + KV bind だけ require)。しかし `GET /mcp/pair/<code>` (browser claim 経路) は `cookie 署名鍵 = env.SESSION_COOKIE_SECRET` を必須とし、未設定の時は **503** を返す:

- `auth-worker/src/index.ts:149` の comment が「未設定 → `/mcp/pair/*` は 503」を明示
- `auth-worker/wrangler.toml:66` 以降の `# Secrets (set via wrangler secret put …)` runbook list に PR #146 で導入された `SESSION_COOKIE_SECRET` の行が **抜けていた** → staging deploy 時に `wrangler secret put SESSION_COOKIE_SECRET --env staging` を実行しそびれた

### Fix (server side)

1. `wrangler.toml` の runbook comment に `SESSION_COOKIE_SECRET` を追記 (本 commit と同 PR で送る)。
2. (手動) `openssl rand -hex 32 | wrangler secret put SESSION_COOKIE_SECRET --env staging` をオペレーターが実行。prod 用も別値で同様に。

## Bug — binary side (install-mcp.sh regex)

`grep -oE 'https?://[^[:space:]]+/mcp/pair/[A-Za-z0-9_-]+'` の `+` (1 文字以上) が `…/mcp/pair/**new**` にもマッチする。binary が pair_url を stdout に出す前に stderr へ `→ pair: POST https://mcp-staging.ippoan.org/mcp/pair/new …` を書くので、merged log を `head -1` で読むと POST endpoint URL が勝つ。これをユーザーが browser で踏むと当然 405 / 404 になり「pair link が腐ってる」と誤解する。

### Fix (binary side)

server 側 `PAIR_CODE_REGEX = /^[A-Za-z0-9_-]{30,60}$/` をミラーして、両 grep を `[A-Za-z0-9_-]{30,60}` に絞る。検証コマンド:

```
$ printf '...mcp-staging.../mcp/pair/new\n...auth-staging.../mcp/pair/64dI…XkxP58QQilYxDEeK\n' \
  | grep -oE 'https?://[^[:space:]]+/mcp/pair/[A-Za-z0-9_-]{30,60}' | head -1
https://auth-staging.ippoan.org/mcp/pair/64dI…XkxP58QQilYxDEeK   ← OK
```

本 commit (PR follow-up) で `.claude/hooks/install-mcp.sh` を修正。

## Server-side unblock — 2026-05-18 ✅

`SESSION_COOKIE_SECRET` をオペレーター (@yhonda-ohishi) が staging + prod の両方に登録済:

```bash
openssl rand -hex 32 | wrangler secret put SESSION_COOKIE_SECRET --env staging   # staging
openssl rand -hex 32 | wrangler secret put SESSION_COOKIE_SECRET                  # prod (top-level)
```

> ⚠️ Gotcha: この repo の `wrangler.toml` は **top-level = prod**、`[env.staging]` が staging override、**`[env.production]` block は存在しない**。最初 `--env=production` を渡して `No environment found in configuration with name "production"` で失敗 → `--env` フラグ無しで再実行で OK。runbook comment はこの hazard を inline 記載する follow-up を auth-worker 側 PR で送付済。

staging + prod とも別値で発行 (rotation policy: ephemeral cookie 鍵なので backup 不要、紛失時は同コマンドで再発行 → 既存 pair session が最大 30 分で切れるだけ)。

これで `/mcp/pair/<code>` 503 ブロッカーは解除。残作業は v0.0.16 tag → 再 smoke のみ (regex fix は v0.0.15 → v0.0.16 で取り込み済)。

### Discoveries / clarifications

- **per-user URL `/u/{login}/mcp` は設計通り正しい**。一時的に「bare `/mcp` の方が正」と疑ったが、auth-worker `src/index.ts:183-209` を読み返すと:
  - `/u/{login}/mcp` = `handleMcpRelayBridge(env, user=login)` → DO bridge (binary attached なら 40+ tools)
  - 素 `/mcp` = ADR-003 user-less variant → 同じ bridge handler に `user=null` で入る (`src/index.ts:203-205`)、DO は JWT の `github_login` claim から id を取る

  両 URL とも binary attach 前は cc-relay stub の 5 tools (`mcp-session-do.ts:753` の `STUB_TOOLS`) を返すのが正しい挙動。install-mcp.sh が書き出す per-user URL を Claude Code Web に登録、で間違っていない。

- **tool list 更新には Claude Code Web 側の再接続が必要**。auth-worker の initialize response は `tools.listChanged: false` (`src/handlers/mcp-tools.ts:384`) なので、binary が後から WS attach してきても client へ `notifications/tools/list_changed` を push しない。pair 完了直後に既存 MCP entry を 1 回 `切断 → 再接続`した時点で tools/list が 5 → 43 に切り替わった。

  CCoW のオペレーション runbook に「pair 後は MCP entry を再接続」の 1 行を足すと事故が減る (本 PR の scope 外、follow-up)。

- **stub のままだった原因の order of events**:
  1. CCoW container 起動 → consumer 側の `.claude/hooks/session-start.sh` から install-mcp.sh を呼ぶ glue が無く、binary が起動しなかった
  2. Claude Code Web は MCP entry を以前から登録済、initial `tools/list` 時に DO は「binary 不在 → stub」を返却
  3. オペレーターから見ると「5 tools しか出ない、URL を bare `/mcp` に変えても増えない」状態
  4. 本 Re-run で `bash .claude/hooks/install-mcp.sh` を手動実行 → binary が pair 待ち → user が pair URL クリック → WS attach → MCP entry 再接続 → 43 tools

  根治: consumer repo (CCoW 経由で使う側) の `.claude/hooks/session-start.sh` から install-mcp.sh を curl しに行く 1 行を template 化。
